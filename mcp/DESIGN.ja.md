# 設計：エージェントのツールを MCP で出す

このモジュールは、ritsu がエージェントのために生成するツール（`requests/mcp/tools.json`）を、MCP のサーバーとして出す。人は自分のエージェントに、資料から申請を出すことや、自分を待っている物を見せることを頼む。エージェントがツールを呼ぶと、モジュールはその呼び出しを、フレームワークの `Server.Do` の一つの操作にし、その人として行う。gate、チケットの版（`revision`）、断りは、画面や API から来たときと同じに効く。チケットの履歴に残るのは人で、エージェントではない。

このモジュールが頼るのは、フレームワークのモジュールと、MCP の Go の SDK（`github.com/modelcontextprotocol/go-sdk` v1.8.0）である。申請の種類ごとのコードは書かない。出す物は、生成した `tools.json` と `openapi.json` から来る。

ここでのエージェントは、人の代わりに動く。申請の種類のステップの中のエージェント（`ask_agent`。`Config.Agents` が動かす）は別の物で、このモジュールは触らない。

英語版：[DESIGN.md](DESIGN.md)。

## 1. 何をするか

- **ツール。** `tools.json` のツールを、そのまま並べる。名前は操作の `operationId` で、題、説明、入力のスキーマ、ヒントはファイルのとおり。ritsu は、申請する人と承認する人の操作と、その人たちが読む物ごとにツールを書く。一覧（`list_requests`、`list_waiting`、`list_mine`）、`get_ticket`、種類ごとの `submit_`（種類が持てば `resubmit_` と `edit_` も）、`approve`、`send_back`、`reject`、`withdraw`、`discard`、`retract`、`comment`、`get_organization`、マスタ（`get_master_*`）、人とチームとマスタの行を言葉で探す物（`find_people`、`find_teams`、`find_master_*`。読むだけで、`readOnlyHint` を持つ）である。チケットを管理する操作（`pause`、`resume`、`add_approver`、`hand_over`）は API にはあるが、ツールは無い。だれが決めるかを変えるか、期限の時計を止める操作で、チケットと組織を読んだ人が自分で行う物だからである（ringi の DESIGN 12.2）。自分のツールを一つだけ足す。変えるツールを、何も保存せずに試す `check_operation` である（8.3）。
- **呼び出し。** 呼び出しを `server.Call` にして `Server.Do` に渡す（3）。答えをツールの結果にする。チケットや一覧は、構造のある内容と短い文に、断りは `isError` の結果と、見る人の言語の断りの文と、フォームの中の場所にする（4）。
- **だれか。** streamable HTTP では、ベアラートークンが人を表す。トークンを人に変えるのは、配置する人が書く関数である。パッケージ `serve` が動かすサーバーの `/mcp` では、ページや API と同じく、サーバーのログインが要求から見つけた人になる（5）。SDK のほかのつなぎ（手元で試すための stdio）では、セッションは一人の人の物で、始めるときにその人を渡す。
- **リソース。** 申請の種類ごとの説明（`types/<kind>.json`）を、リソースとして出す。種類とフィールドの意味を知りたいエージェントのためである（8.2）。

ツールの題と説明（`tools.json`）と、リソースの題は、それぞれの種類を書いた言語のままにする。ツールとリソースの一覧は、セッションの言語で変えない。一つのサーバーは、どのセッションにも同じ一覧を答える。一覧を読むのはエージェントで、どちらの言語で書いた種類のツールも同じように呼ぶ。人に向けて言うのは答えの文で、その言語はセッションの言語（`Config.Language`。ページと同じく `Accept-Language` から読む。2）にし、種類はその言語の題があればその題で言う（4）。一覧を言語ごとにするには、`tools.json` に各ツールの題と説明を言語ごとに持たせること（ritsu は種類の言語だけで書く）と、セッションの言語ごとに一覧を分けることの両方が要る。

## 2. API

```go
import (
	sdkmcp "github.com/modelcontextprotocol/go-sdk/mcp"

	server "github.com/i2y/ringi-server"
	"github.com/i2y/ringi-server/mcp"
)

srv, err := server.New(cfg)
tools, err := mcp.New(srv, mcp.Config{})

// streamable HTTP で、API の横に：
h, err := tools.Handler(mcp.HTTP{Verify: verify})
mux.Handle("/mcp", h)

// または、パッケージ serve が動かすサーバーの /mcp で、そのログインが見つけた人として：
st.Handle("/mcp", func(srv *server.Server) (http.Handler, error) {
	tools, err := mcp.New(srv, mcp.Config{})
	if err != nil {
		return nil, err
	}
	return tools.Handler(mcp.HTTP{Person: serve.Person})
})

// または、一人の人のセッションを stdio で：
err = tools.Serve(ctx, &sdkmcp.StdioTransport{}, server.Person{ID: "e1201"})
```

`Config`：

| フィールド | 何か | 渡さないとき |
|---|---|---|
| `Language` | `func(p server.Person, h http.Header) string`。文と、断りの前置きと、断りの文そのものの言語（`en` か `ja`）。`h` は HTTP の要求のヘッダーで、stdio では nil | ページと同じ選び方（`server.LanguageChoice`）。`Accept-Language` の en と ja のうち、いちばん望まれている方（`server.AcceptLanguages` で、`q` の大きい順、同じ `q` はヘッダーの順で、`q=0` の言語は望まないと読む）。どちらも無ければ、ヘッダーが断っていない限り、組織のデータにあるその人の言語。それも無ければ `en` |
| `Name`、`Version` | MCP の握手で名乗る実装の名前と版 | `ringi-server`、`0.0.0` |
| `Logger` | サーバーの失敗を書くログ | `slog.Default()` |

`HTTP` には、`Verify` と `Person` のどちらか一つを渡す。

| フィールド | 何か |
|---|---|
| `Verify` | `func(ctx, token string, r *http.Request) (Token, error)`。ベアラートークンが表す人を答える。`Token` は、`Person`（役割を含む。`Authenticator` が API に渡すのと同じ形）、`Expires`（ゼロなら言わない）、`Scopes` を持つ |
| `ResourceMetadataURL` | `Verify` と一緒に使う。保護されたリソースのメタデータ（RFC 9728）の URL。401 の `WWW-Authenticate` ヘッダーで知らせる（5） |
| `Scopes` | `Verify` と一緒に使う。トークンが持つべきスコープ。持たないトークンには 403 を返す |
| `Person` | `func(r *http.Request) (server.Person, error)`。要求を送った人を、サーバーのログインが見つけるとおりに答える。パッケージ `serve` のルート（`Stores.Handle`）の後ろでは `serve.Person`、ほかの形で出すハンドラーでは `Server.Authenticate`（5） |

`Verify` も `Person` も無いとき、両方あるとき、`Person` にベアラートークンの設定（`ResourceMetadataURL` か `Scopes`）を添えたときは、`Handler` はハンドラーを作らずにエラーを返す。

`Connect(ctx, transport, person)` は、一人の人の SDK のセッションを返し、`Serve` はそれが終わるまで待つ。試験は、SDK のメモリの中のつなぎで `Connect` を使う。

モジュールは、サーバーのパッケージ（`Server.Packages()`）を読む。パッケージは、自分の requests のディレクトリ（`Package.Files()`）をモジュールに渡す。そこには `openapi.json` と `types/` の横に `mcp/tools.json` が要る。生成したファイルを埋め込む人は、`requests/mcp` も埋め込む。

パッケージの名前は、パスの最後と同じ `mcp` で、SDK のパッケージと同じ名前になる。両方を使うファイルでは、SDK の方を `sdkmcp` と呼ぶ。

## 3. ツールの呼び出しから `Call` へ

ツールの名前が操作（`Call.Operation`）である。引数は、`openapi.json` の操作のパラメーターで分ける。

| パラメーター | 引数 | 行き先 |
|---|---|---|
| ヘッダー `Idempotency-Key` | `idempotency_key` | `Call.Key`。前に `mcp:` を付ける。長いキーは `mcp:sha256:` とキーの SHA-256 にする（6） |
| パス `id` | `id` | `Call.Ticket` |
| クエリ（マスタの `on`、一覧の `limit`、`before`、`kind`） | `on`、`limit`、`before`、`kind` | `Call.Query` |
| （残り） | ほかの引数の全部 | `Call.Body`。一つの JSON のオブジェクト |

引数の名前は、パラメーターの名前を小文字にし、`-` を `_` にした物である。パラメーターの引数は文字列で、ツールの入力のスキーマが型を `integer` にしている所（一覧の `limit`）だけは整数である。整数は、API が本文の整数を読むのと同じに読み（`server.WholeNumber`。`1`、`1.0`、`1e0` はどれも 1）、数字にして渡す。そこに整数でない数（`1.5`）、文字列（`"1"`）、語、`true` があれば、正しくない呼び出しとして答える（「the argument limit is not a whole number」）。範囲（1〜`server.MaxPage`）はサーバーが確かめる。本文は、どの深さでもキーを順に並べ、数は来たままに書き直す。エージェントがキーをどの順で書いても、同じ呼び出しをもう一度送れば、同じダイジェストになる。読む操作は本文を取らない。読む操作のパラメーターでない引数があれば、正しくない呼び出しとして答える。

`New` は、出す前にファイルを確かめる。`tools.json` がパッケージと同じ約束の版を持つこと、どのツールも `openapi.json` の操作であること、操作のどのパラメーターも、ツールの入力のスキーマに引数があること、どの入力のスキーマもオブジェクトであること。合わないパッケージは、何が合わないかを言って断る。

**いくつかの版。** 一つの申請の種類が、いくつかのパッケージに、それぞれの版で入ることがある（フレームワークの `Config.Packages`）。一覧には、どのツールも一度だけ載る。種類のツール（`submit_`、`resubmit_`、`edit_`）は、その時点に `Server.Do` で新しい申請が使う版から取る。`Server.Current` が答える版で、その日に（種類のオフセットで）効いている一番高い版である。効いている版が無い種類は、新しい申請のツール（`submit_` と `worked_`。呼んでも「見つかりません」になる）を一覧に載せず、チケットのツールを一番高い版から取る。`list_requests` は、そういう種類をあとの日から出せる人に、その日を言う（`Server.Offered`。「leave（休暇の申請）は2026-12-01から出せます。」、"leave (Leave request) may be requested from 2026-12-01."）。どの版もこれから始まらない種類については、何も言わない。ほかのツールは、それを持つ最後のパッケージから取る。フレームワークの操作と同じ合わせ方である。古い版のチケットへの呼び出しも通る。フレームワークは、チケットが持つ版で本文を読む。HTTP では要求ごとに一覧を選ぶ。一人の人のセッション（`Connect`）も一覧についてくる。サーバーがほかのパッケージを受け持ったとき（バンドルの承認。フレームワークの DESIGN 15）と、`Config.ChooseEvery` ごと（既定は 1 分。決まった日から効く版や、管理する人の切り替えのため）に一覧を選び直し、違っていれば、変わったツールを外したり足したりする。SDK がセッションに知らせる（`notifications/tools/list_changed`）。パッケージのツールは一度だけ読み、バンドルのツールはサーバーが受け持つ前に読む。ツールが読めないバンドルは断る（`Server.AddPackageCheck`）。

## 4. 答え

| `Server.Do` の答え | `isError` | 構造のある内容 | 文 |
|---|---|---|---|
| OK | false | API の本文そのまま（`{"ticket": …}`、`{"requests": …}`、`{"tickets": …}` など） | チケットの ID、種類、状態、ステップ、だれを待つか。一覧なら、何があるか（下の「一覧」） |
| 断り | true | `{"outcome": "refused", "refused": 種類, "text": 文, "at": 場所}`。場所の無い断りには `at` が無い | 断りの種類の前置きと、次の行に断りの文 |
| 正しくない呼び出し（API の 400） | true | `{"outcome": "invalid", "problem": 問題}` | 「呼び出しの形が正しくないため、受け付けられませんでした」と問題 |
| 見つからない | true | `{"outcome": "not_found", "problem": 問題}` | 「見つかりません」と問題 |
| 制限（API の 429。サーバーがいまは受け付けないコメント。フレームワークの DESIGN 7.4） | true | `{"outcome": "limited", "problem": 問題, "retry_after": 秒}`。待っても変わらないときは `retry_after` が無い | 何秒待ってから同じ呼び出しをやり直すか、または待っても変わらないこと。それと問題 |
| エラー（サーバーの失敗） | true | `{"outcome": "failed"}` | あとで同じ呼び出しをやり直すように言う。エラーはログに書き、見せない |

内容には二つのテキストがある。文と、文字しか読まないクライアントのための、構造のある内容の JSON である。

**探す操作。** `find_people`、`find_teams`、`find_master_<ファイル>_<マスタ>` は、API の探す操作と同じ引数を取り（`q`、`limit`、`lang`、マスタの行なら `on`。フレームワークの DESIGN 9.4）、その本文 `{"found": […], "more": …}` を答える。`lang` が無ければ、セッションの言語で値を名指す。文は、値をラベルで近い順に挙げ（言葉が無いか空白だけなら「ID の順に」「キーの順に」）、ほかにも見つかるときは、言葉を足すように言い、`limit` が 100 より小さければ `limit` を上げるようにも言う。整数でない `limit`（1.5、文字列、配列）は、書かれたままの JSON で渡し、API と同じ順と同じ文で断る（`limit: a whole number from 1 to 100 is expected, not "1.5"`）。一覧の `limit` も同じである。人とチームは、組織にいない人には、API と同じ文で「見つかりません」と答える（フレームワークの DESIGN 9.4）。

- 「近い順に4人見つかりました：営業担当 1（e1201）、営業担当 3（e1203）、営業本部長（e0101）、営業一部長（e3101）。」
- "Found 3 teams, the closest first: Sales Department 1 (sales1), Sales Section 1A (sales1_a), Sales Division (sales_div)."
- 「近い順に5人見つかりました：……。ほかにもあります。言葉を足して絞り込むか、limit を上げてください（100まで）。」`limit` が 100 なら「ほかにもあります。言葉を足して絞り込んでください。」
- 「見つかった人はいません。」、"No row of the master company_masters.vendors is found."

範囲の外の引数は、API と同じ文で、正しくない呼び出しになる（`limit: a whole number from 1 to 100 is expected, not "0"`）。整数でない `limit` は、どのツールも読めない引数を断るのと同じく、呼び出しの前に断る（`the argument limit is not a whole number`）。

文と前置きは、見る人の言語（`Config.Language`）で、英語か日本語である。前置きは、断りの種類が何を意味するかを言う（`stale`：読んだあとでチケットが変わった。もう一度読み、その版で操作する）。断りの文そのものは、種類のコードが答えた文で、API の 409 は英語と日本語の両方を持つ（`text` と `text_ja`。ringi の DESIGN 12.4）。結果には見る人の言語の文を入れ、日本語の文が空なら英語の文を入れる。`at` は API の 409 が言う場所で、断りがフォームのどこの物かを言う。フォームのフィールド（`purpose`）、明細の行のセル（`items[0].price`。行は 0 から数える）、明細の行でフォームが計算するセル（`lines[0].subtotal`。範囲の外になった最初の行）、明細（`lines`。行の数）である。どのフィールドの物でもない断り（ほかの種類の断り、フォームに無い名前）には場所が無く、結果にも `at` が無い。呼び出しのコメントの断り（空か、長すぎる）は、コメントをどのツールで送っても、種類 `comment` で場所を持たない。前置きはその種類で、そう言う。「呼び出しの comment を受け付けませんでした（空か、長すぎます）。フォームの値が理由ではありません。」である。

**一覧。** `list_waiting` と `list_mine` は、API の `GET /waiting` と `GET /mine` と同じく、ページで答える（フレームワークの DESIGN 10.2 と 10.4）。`limit` は一ページのチケットの数の上限で、1〜100（`server.MaxPage`）、無ければ 50（`server.DefaultPage`）である。次のページは、`before` に前のページの最後のチケットの ID を渡して読む。`list_mine` は、`kind` で申請の種類を一つに絞れる。構造化した中身は API の答え `{"tickets": […], "more": …}` で、`more` はページのあとに続きのチケットがあるかである（API は、それを知るために `limit` より一件多く読む）。一覧の文は、チケットを `ID（種類）` の形で、新しい物から挙げる。`more` が真なら、文の最後で、次のページの読み方を最後の ID で言う。「続きがあります。before に <ID> を渡すと、次のページを読めます。」である。最後のページは、`limit` の数まで埋まっていても、次のページのことを言わない。空の一覧は、そう言う（「この一覧に、この人の答えを待っているチケットはありません。」、「この一覧に、この人の申請はありません。」）。英語の文も同じことを言う。`list_requests` の文は、種類を名前と、答えの言語での題で言う。題はサーバーが返す物（`Server.Title`。通知が知らせの種類を言うのにも使う）で、その言語の `labels`、無ければ書いたままの題である（「leave（休暇の申請）」、"leave (Leave request)"）。構造化した中身は、API の答えのまま（題は書いたまま）である。

日本語の文に置く名前（チケットの ID、種類、その題、状態、ステップ、人、操作、日付）は、ページやフレームワークのほかの日本語の文と同じ一つの決まりで置く（フレームワークのパッケージ `internal/jatext`）。ASCII で終わるか始まる名前は、仮名や漢字との間を空白で区切り、全角の約物には空白を置かずに付ける（「チケット 01J…（leave）は in_progress です。」、「leave（Leave request）」）。数は名前ではない。ページと画面と同じく、数は助数詞や単位にも、前の言葉にも空白を置かずに付ける（「申請の種類は10種類です」、「新しい順に次の1件です」、「10秒待ってから」）。この決まりをパッケージに入れないのは、人の ID が数字だけのことがあるからで、文が自分で数をそう書く。

API が 400 で答える本文は、ツールのエラーにする。プロトコルのエラーにはしない。エージェントは問題を読み、本文を直して呼び直す。クライアントは、プロトコルのエラーをモデルに見せないことがあるが、ツールの結果は見せる。

## 5. だれか

**streamable HTTP。** ハンドラーは SDK の streamable HTTP のハンドラーで、前に SDK の `auth.RequireBearerToken` を置く。これが、小さなつなぎを通して `HTTP.Verify` を呼ぶ。

- トークンが無い、`Verify` が `server.ErrNoPerson` を包むエラーを答えた、ID の無い人を答えた：401。`ResourceMetadataURL` があれば、401 の `WWW-Authenticate` で知らせる。
- `Expires` を過ぎたトークン：401。`Scopes` を持たないトークン：403。
- `Verify` のほかのエラー：決まった文で 500。エラーはログに書く。
- API が取る本文（`Config.MaxBody`。無ければ 1 MiB）に、まわりの JSON-RPC のメッセージの分を足したより大きい要求：413。

ハンドラーはステートレスで、JSON で答える。どの POST もそれだけで閉じるので、ロードバランサーの後ろのどのプロセスでも受けられる。SDK が streamable HTTP で MCP の一番新しい版を話すのも、この形のときだけである。GET のストリームは無く、サーバーからクライアントへ要求を送ることも無い。どのツールも、それを要らない。

このモジュールは認可サーバーではない。エージェントが、保護されたリソースのメタデータから認可サーバーを探す場合は、配置する人が SDK の `auth.ProtectedResourceMetadataHandler` を `/.well-known/oauth-protected-resource` に出し、その URL を `ResourceMetadataURL` に書く。そのパスはオリジンの根にあり、そこに何を出すかは配置する人が決める。

**サーバーのログイン。** `HTTP.Person` を渡すと、ハンドラーは要求ごとにそれで人を尋ね、その人を要求のコンテキストに入れる。SDK は要求ごとにセッションを作り、そのセッションの呼び出しにこのコンテキストを渡す。

- `Person` が `server.ErrNoPerson` を包むエラーを答えた、ID の無い人を答えた：401。本文は、フレームワークの API と同じ `{"error":"no one is signed in"}`。`serve` のルートの後ろでは、ルートの検査が先にこう答えるので、ハンドラーには届かない。
- `Person` のほかのエラー：`{"error":"the server failed"}` で 500。エラーはログに書く。
- ページや API と同じく、要求の `Host` は見ない。ループバックのアドレスで待ち受け、前にプロキシを置いたサーバーには、公開の名前が届く。`Verify` のハンドラーのように SDK に任せると、SDK はそれを 403 で断る。決めるのはログインである。フレームワークの、本人を確かめないログイン（`X-Person` ヘッダー、`-dev-login`）は、`Host` がループバックでない要求に人を返さない。そのため、ほかのサイトのページが自分の名前をループバックのアドレスに向けて送ってきても、人のいない要求になる。プロバイダーのセッションのクッキーは、ほかのサイトの名前には送られない。

`serve` が動かすサーバーの `/mcp` では、`serve` のフラグが言う方法で人を見つける。`X-Person` ヘッダー（と `X-Roles`）、`-dev-login` のクッキー、ブラウザでログインしたプロバイダーのセッションである。エージェントは、サーバーのほかのクライアントと同じ物を送る。

**一人の人。** `Connect` と `Serve` は、SDK のつなぎと `server.Person` を取る。手元の stdio では、コマンドが指定した人である。

## 6. 冪等

`tools.json` の変えるツールは、どれも必須の `idempotency_key` を取る。API の `Idempotency-Key` と同じく、1〜255 バイトの、表示できる ASCII（`!` から `~`。空白は無し）である（ringi の DESIGN 12.4。ツールの入力のスキーマにも書いてある）。ほかのキーは、正しくない呼び出しとして答える（「the argument idempotency_key is not 1 to 255 bytes of visible ASCII (from ! to ~, no space)」。空のキーは「the argument idempotency_key is empty」）。モジュールはキーを、前に `mcp:` を付けて、操作のキーとしてフレームワークに渡す。同じ人の、エージェントのキーと画面のキーが重ならないようにするためである。フレームワークのキーも 255 バイトまでなので、`mcp:` を付けると 255 バイトを超えるキー（252 バイト以上の物）は、`mcp:sha256:` とキーの SHA-256 の 16 進にして渡す（`keyOf`）。同じキーは、いつも同じフレームワークのキーになる。フレームワークは、キーごとに答えを保管している。

- 同じキーの同じ呼び出しは、最初の答えを返し、二つ目のチケットを作らない。つなぎのやり直しは同じ呼び出しを送るので、安全である。
- 同じキーで別の引数の呼び出しは、正しくない呼び出しとして答える（「the idempotency key "mcp:…" was used for another operation」）。
- チケットへのイベントは、読んだときの版を持つので、同じイベントを新しいキーで送り直すと `stale` で断られる。`submit_` と `comment` は版を持たない。この二つでは、申請を一つに保つのはキーである。

サーバーの説明（instructions）は、エージェントに、新しい操作には新しいキーを作り、同じ呼び出しを送り直すときは同じキーを送るように言う。

## 7. 記録

履歴の `by` は、画面からのときと同じく人である。どの呼び出しも `Call.Via` を `"mcp"` にして行い、フレームワークはそれを、手と断りの監査ログの記録に残す（`AuditEntry.Via`）。監査ログで、ツールを通った物が分かる。画面を通った物（`"screens"`）とページを通った物（`"pages"`）も同じに分かる。

## 8. 申請する人のエージェントのために

### 8.1 申請の種類を探す

`list_requests` は、その人が今日出せる申請の種類を、題と一緒に答える。ツールの題と説明は、どの `submit_` がどの種類を出すかを言う。「経費の申請」を頼まれたエージェントは、この一覧から種類を探す。種類の説明は、その種類のリソースにある（8.2）。

### 8.2 資料からフォームを埋める

エージェントのモデルは、資料と、`submit_<kind>` の入力のスキーマを読む。フィールド、その型、取る値、必須かどうかである。フィールドが選ぶマスタの行は、`get_master_*` のツールで読むか、`find_master_*` で言葉で探す。フィールドが指す人とチームは、`find_people` と `find_teams` で探す。スキーマが言わないことは、種類の説明にある。ほかの言語のラベル、フィールドを見せる条件と必須にする条件、選択肢のラベル、ステップである。モジュールは、一覧が選んだ版（3）の説明を、リソース `requests:///types/<kind>.json`（`application/json`）として出す。

### 8.3 出す前に食い違いを指摘する

`check_operation` は `{"tool": "<変えるツール>", "arguments": {…}}` を取り、ツールが作るはずの呼び出しを、同じ人、同じ印（`Via` の `"mcp"`）で、フレームワークの `Server.Try` に渡す。`Server.Try` は、`Server.Do` と同じに行い、何も残さない。

- `Do` が読む物（チケット、その時計、組織）を読み、同じ gate、同じ時計で同じ段を通る。本文の形、gate、先に鳴る時計、`start` か `next` である。ストア、処理、通知、監査ログは、元のままである。
- 帳簿には、その呼び出しを受けるかを、取り消すトランザクションの中で尋ねる。確かめは、使い切った予算のような帳簿の断りも見え、帳簿には何も残らない。それができないストアのときや、帳簿が別のデータベースにあるときは、帳簿の呼び出しを尋ねない。答えはそれを `books_not_asked`（呼び出し、帳簿、振替）に並べ、文は、帳簿があとで断るかもしれないと言う。
- 確かめができたときの答えはエラーにしない。`{"outcome": "ok", "saved": false, "ticket": …}`（文は、チケットがだれを待つことになるかを言う）、`{"outcome": "refused", "refused": …, "text": …, "at": …}`（`at` は場所のある断りだけ。4）、`{"outcome": "invalid", "problem": …}`、`{"outcome": "not_found", "problem": …}`（その人が見られないチケットも）、`{"outcome": "limited", …}` のどれかである。一覧の変えるツールでないツールを渡されたときと、サーバーが失敗したときはエラーにする。

冪等キーは要らず、使わない。確かめで見えない物は、確かめと呼び出しのあいだにほかの人がすることである。

### 8.4 サーバーの説明

initialize の答えは、エージェントへの説明を持つ。種類は `list_requests` で探すこと。フィールドはツールの入力のスキーマに、その意味は種類のリソースにあること。変えるツールの前に `check_operation` で試すこと。チケットに何かする前に `get_ticket` で読み、その版を渡すこと。新しい操作には新しい `idempotency_key` を、同じ呼び出しを送り直すときは同じキーを使うこと。

## 9. 試験

例を動かす試験は、例のモジュールにある。`examples/mcp` と、例のコマンドの横の `examples/cmd/mcp` で、そこで `go test ./mcp/ ./cmd/mcp/` と回す。フレームワークのメモリのストアと、例のパッケージと組織を使う（データベースは使わない）。このモジュールに置かないのは、プロジェクトで `go mod tidy` を回すと、読み込んだパッケージの試験も読まれるからである。ここの試験が例を読み込むと、ツールを使うどのプロジェクトも、公開しない例のモジュールが要るようになる。このディレクトリの `go test ./...` が回すのは、例の要らない二つ、版の選び方と、ツールの引数から作る呼び出しである。

- SDK のメモリの中のつなぎでの `tools/list` が、例の `tools.json`（十の種類の 66 のツール。英語と日本語。うち五つは探す物）と `check_operation` であること。
- 例のベクタのうち、人のイベント（`submit`、`resubmit`、`edit`、`approve`、`send_back`、`reject`、`withdraw`、`discard`、`retract`、`comment`）の物を全部、それぞれのサーバーでツールの呼び出しとして送り、断りがベクタの物と同じ種類で同じ場所（`at`）であること、またはツールが答え、ストアが持つチケットがベクタの物で、その人の手としてキー `mcp:vector` で残ること。申請と出し直しの試みの名前は、サーバーがベクタと同じに付ける（`Config.NewAttempt`。`attempt` は引数ではない）。ベクタ 2,990 件のうち 2,058 件がツールを通り、全部合う。うち 10 件は、正しくない呼び出しになる（版の無いイベントで、API が種類のコードより前に 400 で答える本文）。残りはツールの物ではない。時計が 626 件、flow とエージェントの答えが 82 件、チケットを管理するイベントが 220 件、`edit_` のツールの無い種類の `edit` が 4 件である。
- 読むツールが、同じ人に、API が HTTP で答えるのと同じ物を答えること。一覧は `limit` と `kind` を付けたときも。
- 探す操作（`TestFindTools`、`TestFindCalls`、`TestFindCallsMore`）。例の探す操作の五つのツールが、読むだけの物として並ぶこと。11 の呼び出しが、英語と日本語のセッションで API と同じ物を答え、`lang` が無ければセッションの言語で値を名指し、文が上のとおりであること。範囲の外の引数 6 件が、API と同じ文と順で正しくない呼び出しになり、整数でない `limit` がツールの文（`the argument limit is not a whole number`）でそうなること。100 件で、ほかにもある探し方は、言葉を足すようにだけ言うこと。
- `list_requests` が、英語で書いた種類（`leave`）と日本語で書いた種類（`leave_ja`）を、英語と日本語の答えで、答えの言語の題で言うこと。説明に `labels` が無ければ、書いたままの題で言うこと。
- 答えの言語がページと同じであること（`TestLanguageAsThePages`）。`Accept-Language` の一つの表（英語を先に挙げ、日本語をより望む物、`q=0` の日本語、同じ `q`、どちらでもない言語だけ、空）を、パッケージ `web` の開始ページと、HTTP のセッションの両方で読み、どちらも表の言語を選ぶこと。
- gate の断り、古い版、フォームが取らない値、形の違う本文が、断りか問題を持つ `isError` の結果になること。`Language` が `ja` なら、文が日本語であること。
- 日本語の文の中の名前（`TestNamesInJapaneseAnswers`）。説明に `labels` が無く、英語で書いた種類を英語の題で言う場面で、`list_requests`、出したチケットとその読み出しと一覧（`list_mine`、`list_waiting`）、gate による `approve` の断り、組織の版が無い日の断り、組織（`get_organization`）、マスタの行、サーバーが今は受け付けない、続けて送った二つ目のコメントを確かめる。どの行にも、ASCII と全角の約物の間の空白が無く、ASCII の名前が仮名や漢字にじかに付いておらず、数と、隣の仮名や漢字の間にも空白が無いこと。
- 一覧のページ（英語と日本語で）。`limit` を 1 にした `list_mine` が、二つのチケットの新しい方を `more` を真にして答え、次のページの読み方を言うこと。次のページは古い方を持ち、`limit` の数まで埋まっていても、`more` は偽で、次のページのことを言わないこと。最後のページの次は空で、チケットが全部入るページは次のページのことを言わないこと。`limit` が `1.5`、`"many"`、`true` なら、正しくない呼び出しになること。
- コメントの断り（`TestRefusalsOfTheComment`）。2,001 字のコメントを付けた承認は `comment` で断られ、`at` が無く、文は `comment` の前置きと種類の文であること。英語と日本語で。
- 機械の断りの中の名前（`TestNamesInRefusals`）。e1201 が自分の申請を承認すると、組織の部分の名前で「e1201 (Sales staff 1)」「e1201（営業担当 1）」と断られること。組織のデータに名前の無い人は ID だけで言うこと。
- 約束が取るキーの形。255 バイトのキーが通り、同じキーをもう一度送ると同じチケットを、別の 255 バイトのキーは別のチケットを答えること。空白やタブを含むキー、256 バイトのキー、ASCII の外の文字のキーは正しくない呼び出しで、何も作らないこと。
- チケットを見られる人（例の gate で）。申請の種類を受け持つ部門の人は、チケットに名前が無くても、読んでコメントできること。ほかの部門の人と、チケットに名前の無い申請者のチームの人は、どのツールでも（`check_operation` でも）`not_found` になり、チケットの中身は何も返らず、その人たちの物は何も残らないこと。申請者と受け持つ部門の人は承認できない（`person`）こと。`list_mine` が自分のチケットだけを答えること。
- `httptest` での streamable HTTP。トークンが無ければ 401、大きすぎる要求は 413 で、人のエージェントがツールを並べ、一つ呼べること。`Verify` が渡した役割が gate に届くこと。
- `HTTP.Person` を使う形（`TestHandlerByPerson`）。`Verify` と `Person` のどちらも無いときと両方あるとき、`Person` にベアラートークンの設定を添えたときに、`Handler` が断ること。人がいなければ 401、`Person` が失敗すれば 500 で、どちらも本文が API と同じこと。公開の `Host` への要求も受けること。人のエージェントがその人として申請を出し、文が `Accept-Language` に従うこと。
- `serve` が動かすサーバーの `/mcp`（`TestServedByServe`）。`X-Person` ヘッダーと `-dev-login` のそれぞれで、人がいないとき、組織にいない人のとき、もう一方の方法のヘッダーやクッキーのとき、公開の `Host` のときに、ツールに届く前に 401 になること。人のエージェントがツールを並べ、申請を出して読めること。承認する人のエージェントにそれが待っているチケットとして見え、gate が断る `approve` がツールのエラーになること。`X-Roles` の役割が gate に届くこと。
- 同じキーで同じ呼び出しをもう一度送っても、チケットが一つであること。
- `check_operation` が何も保存せず、呼び出しが答えるはずの物を答えること。使い切った予算が見え、帳簿は確かめが尋ねたことを何も残さないこと。
- ツールの呼び出しの監査ログの記録が、人、`mcp:` の後ろのキー、`Via` の `"mcp"` を持つこと。
- 版の始まる日の前後で、種類のツールを取る版の選び方。
- ツールの引数から作る呼び出し。操作、パスのチケット、`mcp:` の後ろのキー、ほかの引数を書かれたままに並べた本文（`1.50` は `1.50` のまま）、マスタの問い合わせ。ツールが取らない引数、オブジェクトでない引数、型の違う値、無いキーと空のキーは誤りになること。
- 例のコマンド（`examples/cmd/mcp`）。何かを読んだり出したりする前に止まる設定と、そのとき言うこと（`TestSettings`）。requests のディレクトリを読む前にその設定で止まり、ディレクトリを読めないときは `-requests` の名前を出すこと（`TestRunStopsFirst`）。

## 10. フレームワークから使う物

- ツールの呼び出しには `Server.Do`、確かめには `Server.Try`（8.3）。どちらも `Call.Via` を `"mcp"` にする。
- パッケージとそのファイルには `Server.Packages()`、種類のツールを取る版には `Server.Current`（3）。
- 一覧の文には、呼び出しが `limit` を渡さないときのページの大きさ `server.DefaultPage`（4）。
- `Language` を渡さないときの答えの言語には `server.AcceptLanguages`（2）、日本語の文の中の名前にはフレームワークのパッケージ `internal/jatext`（4）。

例のモジュールにある例のコマンドと試験は、ほかに次を使う。

- 例のコマンドには、組み込んだ例のパッケージ（`examples.Package()`。`requests/mcp` を持つ）。試験は、同じディレクトリをベクタと一緒にディスクから読む。
- 例のコマンドには、`devlogin` も使う。API の `X-Person` ヘッダー（`devlogin.Header`）と、確かめである。本人を確かめずに人を決めるやり方は、ループバックのアドレスに送られたリクエストにだけ使い（`Local`、`OnLoopback`）、プロバイダーの設定がある所では動かさない（`NotWithProvider`）。
- 試験では、パッケージ `serve`（`Open`、`Stores.Handle`、`Person`）も使う。プロジェクトのコマンドと同じ形で、サーバーの `/mcp` にツールを置くためである。

## 11. あとで

- プロンプト（クライアントのコマンド）は出さない。
