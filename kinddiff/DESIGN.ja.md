# 設計: kinddiff

`kinddiff` は、二つの requests ディレクトリーにある一つの申請の種類を比べる。requests ディレクトリーは `ritsu gen --target requests` が書くもので、このパッケージは、その中の `types/<kind>.json` と `openapi.json` のうちその種類の操作を読む。比べた結果は `Diff` として返し、種類、古い版と新しい版の番号、新しい種類かどうか、変更を読める文にしたものを持つ。文は英語と日本語で答える。

英語版は [DESIGN.md](DESIGN.md) にある。このパッケージは標準ライブラリーだけを使う。

## 1. サーバーが差を自分で作る理由

サーバーは動いているあいだに新しい版のバンドルを受け取る。管理者がそれを認める前に、何が変わるのかを見せなければならない。バンドルの中に説明文を入れてもらうこともできるが、その文はバンドルを作った側の主張でしかない。説明文に一行足りなくても、変わらなかった部分と見分けがつかない。

そこでサーバーは、もともと動かすために読む二つの機械可読な契約から、自分で差を作る。申請の種類の説明と OpenAPI の文書である。同じ二つのディレクトリーからは同じ行が出るので、管理者に見せる前にテストで確かめられる。

## 2. 説明のどこを比べるか

`Compare(old, new, kind)` は、両方のディレクトリーから `types/<kind>.json` を読む。`old` が nil なら、その種類は新しいものとして扱う。種類のファイルがない、説明が JSON のオブジェクトとして読めない、違う種類の説明である、のいずれかなら断る。説明の `name` は比べようとしている種類と同じでなければならない。`name` が変わることは変更として扱わず、違う種類として断る。

説明の最上段にある鍵はすべて比べる。そのうち四つは内容を読み分ける。

- `form`: 項目の追加、削除、移動、ラベル、型、値の範囲、文字数や行数の制限、選択肢、必須かどうか、自動計算かどうか、計算が読む項目、承認者だけが入力するかどうか、入力できる日のカレンダー、見せる条件と必須にする条件。
- `stages`: ステップの追加、削除、移動、ラベル、書かれたままの名前、理由を求める操作を示す `comment_required`、ステップの期限の行、期限を過ぎたステップが上へ回る表。
- `approvers`: ステップが来る場合、承認者の決め方とそれぞれがだれを選ぶかの文、組織の役職とチームの種類、組織の `needs`（`people`、`teams`、`members_of`）、出せる人を決める `submitted_by`、`self_approval`、承認者が直す項目を示す `approvers_edit`。
- `usable`: `effective_from`、`usable.from`、`usable.through`、その日を決める根拠を示す `usable.from_by` と `usable.through_by`、`utc_offset_minutes`。

行の項目は入れ子の中まで比べる。その名前は `items.price` のように点でつないだ ASCII の名前で示す。

ほかの鍵も必ず報告する。`endings`、`events`、`masters`、`flows` には、意味のわかる文を用意する。それ以外の鍵は、中身を推測せず、その鍵の前後の値を示す。ステップや承認者の決め方の中に見知らぬ鍵があっても、名前から規則や期限だと推測しない。`rule` という名前の鍵でも、ritsu が意味を決めるまでは未知の値として `other` に出す。版の番号だけが変わったときは、変更が版の番号だけだと明確に言う。

新しい種類は、空の説明との比較として扱う。項目、ステップ、承認者の決め方、使える日、API の操作がすべて追加として出る。行数は多くなるが、新しい種類を認めることはその形全体を認めることなので、ここでは省略しない。

ラベルは、尋ねられた言語で示す。説明の `label` は元のファイルを書いた言語のもので、`labels` がほかの言語のラベルを持つ。求められた言語のラベルがなければ `label` を使う。ASCII の名前がラベルと違うときは括弧の中に添える。API とファイルでは ASCII の名前を使うからである。

## 3. 承認者の決め方と期限の読み方

ステップの `approvers` は、そのステップが来る場合を経路の順に並べたものである。場合の追加、削除、順の変更を報告し、それぞれの `when`、`who`、`ways`、`kind`、`route` を比べる。場合には安定した機械名がない。そこで、まず変わっていない場合を対応づけ、残ったものは似ているものを変更とみなし、ほかは削除と追加として扱う。一か所を直しただけなのに関係のない場合の削除と追加に見えることを避けつつ、本当に入れ替わったときは削除と追加にする。`ways` の名前は集まりとして比べる。並びが変わっても、その場合が選びうる決め方は変わらないからである。

ステップの `deadlines` は、行の `kind`（`due`、`remind`、`late`、`empty`）で対応づける。同じ種類の行が二度あるときは、書かれた順で対応づける。行の追加と削除、`days`、`calendar`、`written` の変更を報告する。`written` は、期限を過ぎたときや答える人がいないときの動作を機械が読む形である。行には、あわせて前後のページの文を示す。期限の行はステップの進め方の一部なので、`stages` の節に置く。新しい `Line.Section` は増やさない。

最上段の `late_tables` は名前で対応づける。表の追加と削除を報告する。表の中では、変わっていない見出しと行を先に対応づけるので、一行を消しても、そのあとの行がすべて変更には見えない。変わった見出しと行、追加と削除、順の変更を報告する。同じ行の英語と日本語は、一つの変更として一行にする。

これらの規則と期限では、変更の本体に説明が持つ `en` か `ja` の文を使う。サーバーが規則を自分の言葉で言い換えると、もっともらしいのに違う規則になる危険がある。「場合が追加されます」のような枠組みはサーバーが作るが、来るときの条件、答える人の説明、決め方の `how`、期限の文、表の文字は、尋ねられた言語の文をそのまま示す。`ways`、`kind`、`route`、`days`、`calendar`、`written` は機械が読む値なので、文だけに頼らず値として比べる。

これらの値は、組織のデータから実際にだれが承認するかを言うものではない。だれが答えるかは、ステップが始まるときにその日の組織で決まる。ここで比べるのは、決め方と期限の形である。

古い ritsu が書いた説明には、これらの鍵がない。既存の種類で、片方の説明にだけこれらの鍵があるとき、鍵の内容を追加や削除として扱うと、古い版に動作がなかったように見えてしまう。実際には、動作はあったが説明が書かなかっただけである。そこで、変わったかは示せないことを一度言う。ステップの場合と決め方の `how` は、どちらも承認者の決め方の一部なので、説明は一つにまとめて `approvers` に出す。場合が書かれている側では、その説明に並ぶ場合を現在の情報として示す。期限と上へ回る表の説明は `stages` に出すが、変わっていない期限の行や表を並べない。これは変更の報告ではなく互換の断りなので、変わらない行を長く並べると本当の差が見えにくくなるからである。新しい種類ではこの扱いにしない。古い動作がないので、形を追加として示す。

## 4. API の形が変わったとみなすもの

OpenAPI を文字の並びとして比べるわけではない。利用者から見える形だけを比べる。種類の操作ごとに、次のものだけを残す。

- メソッドとパス。
- パラメーターの場所、必須かどうか、形式、スキーマまたは内容。
- 本文が必須かどうか、メディアタイプ、スキーマ、符号化。
- 応答の状態、ヘッダー、メディアタイプ、スキーマ、符号化。

`$ref` は、この選別の前に対象へ展開する。循環する参照は `$ref` の印のまま残し、展開が終わらない事態を避ける。ヘッダーとメディアタイプの名前は小文字に揃える。説明文、題、例、非推奨の印、読み書きの注記、`x-` で始まる拡張、操作の要約、`x-ritsu-request` は、送受信する JSON の形ではないので除く。オブジェクトの鍵の順は意味に入れない。`required` や `enum` のようなスカラーの配列は、順に意味がないので集まりとして比べる。

操作がその種類のものかは、まず `x-ritsu-request.name` で見る。古い生成物にはこの印がないことがあるので、`/requests/<kind>/` で始まるパスか、その種類と同じタグを持つ操作もその種類のものとみなす。チケットや組織の共有操作は、その種類の変更としては出さない。ただし共有スキーマをその種類の操作が参照しているなら、展開した結果はその操作の形に入る。共有スキーマの変更がその種類に影響するときは、正しく API の変更になる。

`APIChanged()` は、`api` の節に行があるとき true になる。操作の追加や削除、メソッドやパスの変更、パラメーターの変更、本文や応答の変更、スキーマの制約の変更がこれにあたる。画面に見える承認の流れが同じでも、利用側のプログラムや画面が wire 上の形に依存していることがある。そのため管理者には、この節を特に確かめてもらう必要がある。

## 5. 行の順と言語

`Lines(lang)` は行の複製を返す。`lang` が `"ja"` なら日本語で、それ以外なら英語で答える。順は決まっていて、`form`、`stages`、`approvers`、`usable`、`api`、`other` の順である。節の中では、説明に書かれた順、または `openapi.json` に操作が書かれた順に並べる。

それぞれの `Line` は節を持つ。API の行では `API` が true なので、呼び出し側は節で分けるだけでなく、API の形の確認を別に求められる。

## 6. 実際の出力

`example_test.go` の `ExampleCompare` は、`kinddiff/testdata` に置いた、実際に生成された `leave` の版 1と版 2を比べる。これらは ritsu 0.56.0 の `ritsu gen --target requests` が書いたもので、承認者、期限、決め方、上へ回る表の鍵を持つ。`kinddiff/testdata/old` には、これらの鍵を書く前の ritsu が書いた版 1 を置く。古い説明と新しい説明の比較に使う。Go の example テストが、この出力をそのまま検査している。

```text
form api=false: The range of the field "Business days" (days) changes from 1 through 20 to 1 through 25.
usable api=false: This version now takes effect from 2027-04-01.
usable api=false: The first day the kind can be used changes from 2026-04-01 to 2027-04-01.
usable api=false: The data deciding the first day the kind can be used changes from "the first version of the organization `shared/company.ringi` (data `../org`)" to "`effective from`".
api api=true: In the request body of `submit_leave`, `maximum` of `form.days` changes from `20` to `25`.
api api=true: In the request body of `resubmit_leave`, `maximum` of `form.days` changes from `20` to `25`.
other api=false: The version number changes from 1 to 2.
form api=false: 項目「営業日の日数」（days）の範囲が1以上20以下から1以上25以下に変わります。
usable api=false: この版は2027-04-01から効きます。
usable api=false: この申請の種類を出せる最初の日が2026-04-01から2027-04-01に変わります。
usable api=false: 申請を出せる最初の日を決めるデータが「the first version of the organization `shared/company.ringi` (data `../org`)」から「`effective from`」に変わります。
api api=true: `submit_leave`に送る本文では、`form.days`の`maximum`が`20`から`25`に変わります。
api api=true: `resubmit_leave`に送る本文では、`form.days`の`maximum`が`20`から`25`に変わります。
other api=false: 版の番号が1から2に変わります。
```

二つの版では承認者と期限の鍵の内容が同じなので、この出力にはそれらの行がない。詳細なテストでは、この実際の説明の写しを変えて、それぞれの変更を確かめる。空でない上へ回る表は、実際に生成された `expense` の表を使う。表の行や見出しを変えたものはテスト用の写しで、別の版を ritsu が生成したものではない。

## 7. 省いたもの

画面、MCP の道具、ベクタ、マスタのデータ、組織のデータは読まない。これらは配置したサーバーの見え方や動作に関わるが、申請の種類そのものの説明でも、wire 上の API でもない。バンドルにこれらを含めて承認の対象にするなら、別の表示が必要になる。

知らない鍵は推測して読まない。生成側が意図していない意味をこちらで作らないためである。`masters` と `flows` の内部でも、名前のある項目より深い部分は、細かく解釈せず前後の値で示す。

説明の `name` の変更は、差の一行としては出さない。ファイルは `types/<kind>.json` という場所で指定し、`name` はそのファイルが本当にその種類を説明しているかを確かめる印だからである。違う名前は変更ではなく、違う種類として断る。

文のテストには golden ファイルを使わなかった。画面のような大きな構造出力とは違い、ここでは文そのものが成果物である。テストでは英語と日本語の重要な部分を直接確かめ、`ExampleCompare` で実際の例の出力を一字一句固定している。
