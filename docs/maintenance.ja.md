# バックアップと版の上げ方

動いているサーバーのデータを守り、新しくしていくための手引きです。英語版は [maintenance.md](maintenance.md) です。

## バックアップ

次のものは、すべてデータベースにあります。

- 申請と履歴、添付ファイル
- 期限のタイマー、まだ送っていない通知や処理
- 組織のデータ、管理の記録
- 予算などの帳簿（同じデータベースに置いているとき）

互いに食い違わないよう、データベース全体を一度にバックアップします。

```sh
pg_dump --format=custom --file=ringi.dump ringi
```

クッキーの鍵（`RINGI_SESSION_KEYS`）と、プロジェクトの Git のリポジトリも、別に保管しておきます。

## 復元

1. サーバーのプロセスを、すべて止めます。
2. 空のデータベースを作り、権限を与えて、復元します。

    ```sh
    createdb ringi_restored
    psql -d ringi_restored -c 'grant create on database ringi_restored to ringi_server'
    pg_restore --dbname=ringi_restored --exit-on-error ringi.dump
    ```

3. `-db` を新しいデータベースに替えて、サーバーを起動します。

復元すると、すべてがバックアップの時点に戻ります。起動する前に、次のことを知っておきます。

| こと | どうなるか |
|---|---|
| バックアップのあとの申請と承認 | 失われる。もう一度行ってもらう |
| バックアップのあとに過ぎた期限 | 起動するとすぐに処理される。そのあいだに承認されていた申請も、復元では待っている状態に戻るので、期限切れになることがある |
| バックアップの時点で送る前だった通知や処理 | 起動したサーバーが送る。すでに送っていたものも、同じキーでもう一度送られる。受け取る側がキーを覚えていれば、二重にはならない |
| バックアップのあとに始まった支払いなど | 取り消されない。その申請をもう一度承認すると、もう一度始まることがある |

起動と同時に処理される期限と催促の件数は、起動する前に、次の SQL で分かります。

```sql
select count(*) from ringi.timers where at < now();
```

## 版を上げる

### ringi-server と ritsu

二つは組で上げます。組み合わせは、[版の表](../README.ja.md#版)にあります。

1. プロジェクトで、ritsu と ringi-server を新しくして、コードを作り直します。`v0.1.0` は、上げる先の版に替えます。

    ```sh
    brew upgrade ritsu
    go get github.com/i2y/ringi-server@v0.1.0
    go generate ./...
    go mod tidy
    go test ./...
    ```

    モジュール `mcp` と `temporal` を使っているなら、それも同じ版にします。

2. 古いサーバーのプロセスを、すべて止めます。
3. データベースをバックアップします。
4. 新しいサーバーを起動します。起動のときに、データベースの表を一つのトランザクションで新しくします。

古いサーバーは、新しくなった表では起動しません。前の版に戻すには、バックアップを復元します。

### 申請の種類などを変えたサーバーに入れ替える

申請の種類、カレンダー、権限の決まり、Go のコードを変えたときは、サーバーを作り直して入れ替えます。進行中の申請に影響させたくない変更は、先に[申請の種類の版を上げます](types.ja.md#使われている申請の決まりを変える)。

1. 検査し、コードを作り直し、試験して、ビルドします。

    ```sh
    ritsu check project
    go generate ./...
    go test ./...
    go build -o server ./cmd/server
    ```

2. 古いサーバーのプロセスを、すべて止めます。
3. 新しいサーバーを起動します。

止めているあいだに過ぎた期限は、起動したときに処理されます。

古いプロセスと新しいプロセスを一緒に動かすと、新しい種類や版の申請を、古いプロセスでは開けません（サーバーのエラー、500 になります）。新しい版の申請が出たあとで前の実行ファイルに戻したときも同じです。

### 古い版のコードを外す

古い版のコードは、その版の申請が一件でもあれば外せません。終わった申請を開くときにも、その版のコードを使うからです。申請を消す操作はないので、一度でも使われた版のコードは、ずっと残すことになります。

どの版の申請がいくつあるかは、管理のページの「チケット（進行中／全部）」に出ます。データベースでは、次の SQL で分かります。

```sql
select kind, version, count(*) as all_tickets,
       count(*) filter (where status in ('in_progress', 'paused', 'with_requester')) as in_progress
from ringi.tickets group by kind, version order by kind, version;
```

## 組織のデータ

異動や入社のデータは、動いているサーバーに、管理のページから取り込みます（[異動のデータを取り込む](use/admin.ja.md#異動のデータを取り込む)）。サーバーを止める必要はありません。

プロジェクトの `project/org/` にも、同じものを加えておきます。サーバーが起動するときは、組み込まれたデータを次のように扱います。

| 組み込まれたデータ | 起動のとき |
|---|---|
| 前に組み込まれていたものと同じ | 取り込まない。管理のページで取り込んだデータが、そのまま使われる |
| 前に組み込まれていたものと違う | 取り込む。管理のページで取り込んだデータは、これに替わる |

管理のページから取り込んだものを `project/org/` に入れ忘れると、次に `project/org/` を直したときに、取り込んだものが消えます。

## 残るものと、その期間

サーバーは、期間の過ぎたものを、起動のときと 1 時間ごとに自分で消します。

| もの | 期間 |
|---|---|
| 申請と履歴、申請が持つ添付ファイル、組織のデータ、管理の記録、済んだ通知や処理の記録 | ずっと |
| どの申請も持たない添付ファイル | 7 日 |
| 操作の番号と応答 | 30 日。そのあいだに同じ番号で送り直すと、同じ応答が返る |
| 確かめただけで取り込んでいない、組織のデータ | 1 日 |
| ログアウトしたセッションの記録 | そのセッションの期限まで |

申請と履歴を消す操作はありません。件数が増えたときの表の大きさは、[データベースを見る](troubleshooting.ja.md#データベースを見る)の SQL で分かります。
