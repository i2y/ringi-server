# ログインをつなぐ

社員に使ってもらうサーバーでは、会社のログインを使います。OpenID Connect に対応したログインのサービスなら、フラグを渡すだけでつながります。英語版は [sign-in.md](sign-in.md) です。

## ログインの三つの方法

| 起動のしかた | だれのリクエストか | 使うとき |
|---|---|---|
| `-dev-login` | ページで選んだ人 | 自分のコンピューターで画面を試す |
| `-oidc-…` のフラグ | 会社のサービスでログインした人 | 社員に使ってもらう |
| どちらも付けない | ヘッダー `X-Person` に書いた人 | 自分のコンピューターで API を試す |

`-dev-login` と `X-Person` は、本人かどうかを確かめません。そのため、自分のコンピューターのアドレスでしか動かず、プロキシが転送したリクエストは受け付けません。

手前のプロキシがログインさせているとき、プログラムのトークンを受け付けたいときは、サーバーを自分で組み立てます（[自分のプログラムに組み込む](embedding.ja.md)）。

## 1. ログインのサービスに登録する

ログインのサービスを管理している人に、次の内容で、クライアント（このサーバーの登録）を作ってもらいます。

| 項目 | 値 |
|---|---|
| 種類 | シークレットを持つ Web アプリケーション（認可コードフロー） |
| リダイレクト URI | 社員が開くアドレスに `/login/callback` を付けたもの。ポートがあれば、それも入れる（例：`https://ringi.example.com:8443/login/callback`） |
| スコープ | `openid email profile` |
| ID トークンに入れるクレーム | `email`、`email_verified`、人の役割のリスト |
| ID トークンの署名 | RS256、PS256、ES256 のどれか |
| クライアントの認証 | `client_secret_basic` か `client_secret_post` |

受け取るのは、issuer の URL、クライアント ID、クライアントシークレットの三つです。

## 2. 組織のデータにメールアドレスを入れる

サーバーは、ログインした人を、組織のデータからメールアドレスで探します。`people.csv` の `email` の列に、ログインのサービスが確認済みとしているアドレスを入れます。大文字と小文字の違いは区別しません。

## 3. 設定を渡す

ログインした人のクッキーを暗号化する鍵を作ります。作るのは一度だけで、出た値を保管し、起動のたびに同じものを渡します。なくすと、全員がログインし直すことになります。

```sh
head -c 32 /dev/urandom | base64
```

クライアントシークレットと鍵は環境変数で、ほかはフラグで渡します。

| 渡すもの | 環境変数、フラグ |
|---|---|
| クライアントシークレット | `RINGI_OIDC_CLIENT_SECRET` |
| クッキーの鍵 | `RINGI_SESSION_KEYS` |
| issuer の URL | `-oidc-issuer https://id.example.com` |
| クライアント ID | `-oidc-client-id ringi` |
| リダイレクト URI | `-oidc-redirect-url https://ringi.example.com:8443/login/callback` |
| 役割が入るクレームの名前 | `-oidc-roles-claim roles` |

起動のコマンドの全体は、[用意して起動する](operations.ja.md#3-起動する)にあります。

issuer は、`<issuer>/.well-known/openid-configuration` の文書に書かれたとおりに渡します。末尾の `/` の有無が違うだけでも、サーバーは起動しません。

## 4. 役割を渡す

申請を管理する役割（`workflow_admin`、`system_admin`、`auditor`）は、ログインのサービスの側で人に付けます。どの役割で何ができるかは、[だれが何をしてよいかを決めるもの](concepts.ja.md#だれが何をしてよいかを決めるもの)にあります。役割が入るクレームの名前を `-oidc-roles-claim` で渡します。値は、文字列か、文字列のリストです。

- 役割を付けた人も、社員としてできることは変わりません。役割が一つもない人は、ふつうの社員（`staff`）です。
- サーバーが使うのは、権限の決まり（`project/shared/company.gate`）にある役割だけです。ほかの値は無視され、そのことが一度だけログに出ます。
- 付けたり外したりした役割は、その人が次にログインしたときから効きます。
- グループを ID で渡すサービスでは、その ID が役割の名前になります。権限の決まりを、その値に合わせて書きます。
- 役割はクッキーに入ります。会社のグループを全部入れるとクッキーに入りきらず、ログインできません。このサーバーの役割だけを渡します。

## 5. 確かめる

1. ブラウザでホームを開くと、会社のログインに移り、済むとホームに戻ります。
2. ページの上に、自分の名前が出ます。
3. 役割を付けた人のホームに、「管理」のリンクが出ます。

ログインできなかったときは、ページに出た理由とログを見ます。

## ログインした人に見えること

ログインしていない人がページを開くと、ログインのサービスに移り、終わると元のページに戻ります。ログインした状態は、ログインから 12 時間か、使わないまま 2 時間で終わります。「ログアウト」は、どのページの上にもあります。

次の人はログインできません。理由がページに出て、ログにも残ります。

| 理由 | ログの `reason` |
|---|---|
| メールアドレスを、ログインのサービスが確認していない | `no_verified_email` |
| そのアドレスの人が、組織のデータにいない | `not_in_organization` |
| そのアドレスの人が、二人以上いる | `ambiguous_email` |

次は[用意して起動する](operations.ja.md)で、ほかの準備と合わせて起動します。
