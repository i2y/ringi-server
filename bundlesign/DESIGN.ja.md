# 設計：バンドルの署名（bundlesign）

パッケージ `bundlesign` は、申請の種類のバンドルに署名し、その署名を確かめる。バンドルは、requests ディレクトリと Wasm モジュールを zip にしたファイルで、サーバーが受け取るときのバイト列のまま扱う。このパッケージは標準ライブラリだけを使う。英語版は [DESIGN.md](DESIGN.md) である。

サーバーが署名を確かめるのは、設定に ed25519 の公開鍵が並んでいるときだけである。その一覧が、どの鍵を信じるかという決まりである。署名が合えば、対応する秘密鍵を持っていた人が、そのバイト列に署名したことが分かる。公開鍵を設定していなければ、署名が無くても、それだけではバンドルは拒否されない。バンドルを受け取るかは、サーバーのほかの確かめと承認の流れが決める。公開鍵を設定していても、署名が合うことだけでは、だれがバンドルを上げたか、使えるようにしてよいかは分からない。

## 1. 署名するもの

バンドル全体の SHA-256 を、小文字の 16 進で書く。

```go
func Digest(bundle []byte) string
```

署名が対象にするバイト列は、次の二行である。

```text
ringi bundle v1
<the 64 hexadecimal digits of Digest(bundle)>
```

つまり、文字列では `"ringi bundle v1\n" + Digest(bundle) + "\n"` である。

ダイジェストがあるので、署名は zip のすべてのバイトに結び付く。同じファイルを入れていても、並びやメタデータが違う zip は、署名では別のバンドルである。これは意図した動きである。サーバーは、このファイルそのものを受け取り、保管し、配る。zip の中身を解釈したものではなく、受け取ったバイト列に署名する。

頭の決まった文字列は、用途を分けるためにある。同じ鍵を使うほかのもの、たとえばリリースの文や Git のコミットに付けた署名を、バンドルの署名と取り違えないためである。`v1` があるので、あとで署名するものを変えるときに別の文字列を使える。あとの形式がまったく同じ意味でない限り、この文字列を使い回してはいけない。

バンドルそのものではなくダイジェストに署名するのは、署名する文を短く一定にするためである。秘密鍵が行う計算はバンドルの大きさによらず、確かめる側も、署名した文が何かを正確に言える。ここで SHA-256 をパスワードや鍵のために使うわけではない。必要なのは衝突に強いことで、フレームワークのほかのところでも使っている標準のダイジェストである。

## 2. ファイルの形

### 署名のファイル

`Sign` は `<bundle>.sig` の中身を返す。

```go
func Sign(key ed25519.PrivateKey, bundle []byte) []byte
```

ファイルは、標準の base64 の一行で、最後に改行が付く。base64 をデコードすると、64 バイトの ed25519 の署名である。鍵の ID、アルゴリズムの名前、時刻、コメントは入れない。アルゴリズムは固定で、鍵は確かめる側が選ぶ。署名した時刻は、受け取るかの判断には使わない。

`Verify` はファイルを厳しく確かめる。

```go
func Verify(keys []ed25519.PublicKey, bundle []byte, sig []byte) error
```

base64 の行のあとに何も付かないもの、改行が付くもの、CRLF が付くものを受け付ける。余分な行、空行、行のまわりの空白、長さの違う署名の base64、標準形ではない base64、行の前後にあるほかのデータは受け付けない。厳しくするのは、サーバーがこの小さなファイルをそのまま扱うためである。寛容に読む実装があると、見た目が違う二つのファイルが、実装ごとに違う意味を持ちかねない。

並んだ公開鍵のどれか一つで署名が合えば、確かめは成功である。鍵を変える途中や、組織が複数の署名鍵を認めるときに、複数の鍵が必要である。確かめる側は、どの鍵が使われたかを知らなくてよい。

### 秘密鍵

`keygen` は、秘密鍵を一つの PEM ブロックで書く。

```text
-----BEGIN PRIVATE KEY-----
…
-----END PRIVATE KEY-----
```

ブロックは PKCS#8 で、`crypto/x509.MarshalPKCS8PrivateKey` が書く形である。`ReadPrivateKey` は、この形のブロックをちょうど一つだけ読む。別の種類のブロック、複数のブロック、ブロックの外にあるデータ、ed25519 でない鍵は受け付けない。コマンドは、このファイルを mode 0600 で書き、すでにあるファイルを上書きしない。

### 公開鍵

公開鍵のファイルは、一つ以上の PEM ブロックである。

```text
-----BEGIN PUBLIC KEY-----
…
-----END PUBLIC KEY-----
```

どのブロックも PKIX で、`crypto/x509.MarshalPKIXPublicKey` や一般的な鍵のツールが書く形である。ブロックを連ねると、複数の鍵を並べられる。`ReadPublicKeys` は、別の種類のブロック、ed25519 でない鍵、ブロックの外にあるデータ、ブロックの無いデータは受け付けない。

## 3. ed25519 と PEM にした理由

ed25519 は Go の標準ライブラリにあり、鍵と署名が小さく、アルゴリズムや曲線を選ぶ必要がない。同じバンドルに同じ鍵で署名すれば、毎回同じ署名ができる。出力が変わったときに気づきやすい。鍵と署名の長さが決まっているので、ファイルの形も確かめやすい。

PEM を使うのは、標準ライブラリと一般的な鍵のツールがすでに書くテキストの形だからである。PKCS#8 と PKIX にはアルゴリズムが入っている。RSA や ECDSA の鍵が入ったファイルを、読み違えずにエラーにできる。PEM ブロックは連ねられるので、公開鍵のファイルに新しいファイル形式を作らずに、複数の鍵を入れられる。

## 4. 入れなかったもの

### zip の中に署名を入れる形

zip の中に入れた署名は、zip 全体を対象にできない。署名を足すと zip が変わるからである。対象を選ぶか、署名するファイルの一覧を作る必要がある。確かめる側は、zip のどの要素とメタデータに意味があるかの決まりを知っている必要がある。zip を書く側にも、署名する側と確かめる側が同じバイト列を対象にできるような、決まりを持った書き方が要る。

外側の `.sig` なら、この循環を避けられる。zip は署名した人が見たファイルのままであり、ダイジェストはメタデータを含む全部を対象にする。論理的に同じ中身の zip が別の署名を持つことがあるのは、この形の弱点である。ただしサーバーはファイルそのものを配布物として扱うので、この弱点は受け入れられる。

### 証明書と期限のある鍵

証明書は鍵を名前に結び付けるが、証明書の連なり、信頼の起点、失効、時刻への依存を持ち込む。ここでは、サーバーに設定した鍵の一覧がすでに信頼の起点である。証明書の中の名前があっても、サーバーが新たに決められることはない。期限を付けると、それまで必要なかった時計に確かめが依存する。期限の切れた鍵のために、正しいバンドルを読めなくなることもある。

鍵の変更は運用で行う。新しい公開鍵を先に足し、古い鍵の署名を受け付けなくするときに古い鍵を外す。証明書が要る環境では、この形式の外で証明書を管理し、その公開鍵をここに設定すればよい。

### 外の署名サービス

署名サービスや鍵の管理サービスを使うと、秘密鍵を運用する人のコンピューターに置かずに済む。しかし、フレームワークのパッケージに認証、可用性、ネットワークの決まりを持ち込む。このパッケージとコマンドは、標準ライブラリだけを使ってオフラインで動く、小さなものに留める。そうしたサービスに鍵を置く組織は、サービスに ed25519 の署名を作らせ、サーバーに渡すファイルだけこの形に合わせることができる。
